# dbeans — Architecture

## 1. Overview

dbeans is a Go backend (JSON API) plus a React frontend. Unlike the original plan, dbeans now depends on one external service by design: a Postgres database (currently [Neon](https://neon.tech)) that owns **dbeans' own account/session/analytics data** — it is not a target database the user browses, it's dbeans' operator database. Target databases (the ones the user actually inspects) are configured separately per connection and support SQL engines plus Redis and Kafka.

```
Browser (React SPA)
      │  HTTPS
      ▼
Go backend
 ├─ Auth (bcrypt password hash + bearer session tokens, stored in Postgres)
 ├─ REST API (auth, analytics events, connections + reachability ping, schema,
 │            query execution, structured table browsing/CRUD, scheduled jobs + tick endpoint)
 ├─ Driver abstraction layer
 │    ├─ database/sql compatible ── pgx (PostgreSQL, real — see §2) · go-sql-driver (MySQL/MariaDB, planned) · modernc sqlite (SQLite, planned)
 │    ├─ go-redis                 (Redis: real key browse/edit + TTL operations)
 │    └─ segmentio/kafka-go       (Kafka: real topic/message browse + produce)
 └─ Operator DB (Postgres, e.g. Neon) — DATABASE_URL from env
      - users, sessions               (real auth, not a demo)
      - analytics_events              (sign-ins, query runs, ...)
      - connections                   (saved connections + canvas layout + reachability status)
      - jobs, job_runs, job_queue     (typed scheduled jobs, run history, and the pending-dependency queue — see §6)
      - saved_queries, saved_views    (per-user saved workbench queries; named Data-browser views — see §4)
      - query/mutation history        (read back from analytics_events; app settings still client-side)
                      │
                      ▼
   User's target sources: Postgres / MySQL / SQLite / Redis / Kafka
```

## 2. Backend (Go)

- **Language/runtime:** Go, compiled to a single static binary.
- **Redis and Kafka:** real authenticated clients are wired through connection-scoped API routes. Redis supports TLS, logical database selection, SCAN-based key discovery, string/hash/list/set/zset editing, TTL changes, create and delete. Kafka supports multiple brokers, TLS, SASL/PLAIN, topic metadata, bounded recent-message reads, producing to a selected partition, and polling-based live tail. Both deliberately cap browser payloads (500 Redis keys/members and 100 Kafka messages).
- **HTTP framework:** `chi` (`github.com/go-chi/chi/v5`) — no need for a heavier framework given the API surface is modest.
- **Driver abstraction (partially built):** the original plan is a `database/sql`-based abstraction shared across Postgres/MySQL/SQLite. **Current state:** only Postgres is wired up, directly via `pgx` (`backend/internal/api/query.go` and `table_data.go`), not yet behind a generic `Driver` interface — `GetConnectionSchema` introspects `information_schema` for tables/columns/views plus primary/foreign keys, `RunConnectionQuery` executes arbitrary SQL and returns up to 1000 rows, and the structured table-data API provides server-paginated browsing plus insert/update/delete. MySQL/SQLite connections can be created and pinged but fail at query/schema/data time with an explicit "not wired up yet" error rather than silently returning nothing. **Not yet built:** query cancellation and server-side pagination/streaming for arbitrary freeform query results (the 1000-row cap remains a blunt stand-in there; table browsing itself is paginated).
- **Structured table-data API:** `POST /api/connections/{id}/table-data` accepts a schema/table, validated filters and sort columns, page, and page size (capped at 500), then returns rich live column metadata (type, nullability, default, primary/foreign key, enum, identity/generated state), text-or-null rows, and a filtered total count. `POST`, `PATCH`, and `DELETE /api/connections/{id}/table-rows` insert, update, and delete one row; `POST /api/connections/{id}/table-rows/bulk-delete` accepts 1–500 complete row keys and deletes them in one transaction. Every route resolves the saved connection server-side and introspects the target table/view before generating SQL; values are bind parameters and identifiers are passed through `pgx.Identifier.Sanitize()`. Updates/deletes require exactly the complete real primary key, so a missing composite-key component cannot broaden a mutation. Views are browse-only, and the backend independently rejects every mutation for a read-only connection. `POST /api/connections/{id}/schema-change` is the narrow execution path for previewed visual schema actions. See [DATA_EDITOR_TESTING.md](DATA_EDITOR_TESTING.md) for the complete acceptance and negative-test matrix. (A 2026-09-18 query-optimization pass confirmed the browse query's `SELECT *` — bounded by the same page-size cap, never an unbounded table read — is the *only* `SELECT *` anywhere in the backend; it's deliberate, since the browser can't know in advance which columns the user wants and column show/hide is a client-side-only preference that intentionally never triggers a refetch. Every other backend query, including every job's own SQL currently configured in production, selects explicit columns.)
- **Data-editor audit trail & query history (2026-09-18):** every Data-view mutation (`InsertTableRow`, `UpdateTableRow`, `DeleteTableRow`, `BulkDeleteTableRows`, `ExecuteSchemaChange`) now logs to `analytics_events` through the same `analytics.LogEvent` helper `login`/`logout` already used — event types `row_insert`, `row_update`, `row_delete`, `bulk_row_delete`, `schema_change`, alongside the pre-existing frontend-logged `query_run`. `InsertTableRow`'s SQL gained a `RETURNING *` so both the audit payload and the frontend's Undo know the row's real committed values, including any database-generated default/identity the request never supplied — without it, an inserted row's generated primary key would be unknown to both. `GET /api/connections/{id}/history` (`backend/internal/api/history.go`) reads this same table back, scoped to the requesting user's own events for one connection via `payload->>'connectionId'` (there's no dedicated `connection_id` column — every writer already includes one in its JSONB payload), and powers a new **History** tab alongside Query/Data/Graphs/ERD in the workbench.
- **Row counts, cancellation, and CSV import (2026-09-21):** opening a table must never begin with a full `count(*)`. `BrowseTableData` therefore picks the cheapest *honest* count and says which it is in `totalKind`: an unfiltered base table whose `pg_class.reltuples` estimate is ≥ 50,000 (`countCap`) returns that estimate (`estimated`) without touching the table; everything else counts at most `countCap` rows (`SELECT count(*) FROM (SELECT 1 … LIMIT 50001)`) under a 3 s `statement_timeout`, yielding `exact`, `lower-bound` (`N+`), or `unknown` on timeout. The timeout is `SET LOCAL` inside a transaction, so it can never leak onto the connection's later queries (covered by a DB-backed test). The page query fetches `pageSize+1` rows so `hasMore` is always exact even when the total isn't — Next/Previous depend on it, not on the total. `countMode: "skip"` lets the client reuse the total it already holds when only the page or sort changed (the client keys a total by table + applied filters). "Count exactly" is a separate endpoint, `POST …/table-data/count` (15 s limit, HTTP 504 on timeout), so it can be cancelled without disturbing the page. **Cancellation is real:** the frontend passes an `AbortSignal` to every page load and count; aborting the `fetch` closes the request, Go cancels `r.Context()`, and pgx cancels the Postgres query (verified: an aborted slow query is gone from `pg_stat_activity` within a second). Every new load aborts the previous one, and a sequence number additionally discards any response that resolves after being superseded, so a slow table's late reply can never overwrite a newer view. **CSV import** (`table_import.go`): the browser parses the file (`lib/csv.ts`, RFC 4180 with delimiter sniffing; an unterminated quote is an error, not silent data loss), the user maps columns, and the client sends rows already aligned to target columns. The server validates the request (columns exist and aren't generated/identity, none repeated, every NOT NULL-without-default column covered, ≤ 10,000 rows, ≤ 8 MB), then runs one `INSERT` per row pipelined as a single `pgx.Batch` inside one transaction — values are bound text parameters, so Postgres parses each into its column type exactly as the row editor does. A dry run always rolls back; a commit is all-or-nothing. On failure it keeps hunting for more bad rows by re-running the file minus the rows already known to fail (up to 20 errors, inside an 8 s budget), so one validation pass surfaces many problems instead of one at a time; data problems are a normal HTTP 200 with `ok: false` and per-row `errors`, reserving 4xx for malformed requests. Committed imports log a `table_import` audit event (table, columns, row count — never the row contents). No Undo: an import is many rows across unknown keys, and the confirm dialog says so.
- Generalizing today's Postgres-only code into a real multi-engine `Driver` interface is the extension point for adding MySQL/SQLite/MSSQL etc. without touching the API or frontend contracts.
- **Frontend embedding:** the built React app (static JS/CSS/HTML) is embedded into the Go binary via `go:embed`, so `docker run dbeans` (or a single copied binary) serves both API and UI on one port.
- **Realtime/streaming (planned, not built):** a WebSocket (or SSE) connection per active query tab, used to push query status (running/done/error), elapsed time, and cancellation support without polling. Query execution today is a plain synchronous HTTP request/response.

## 3. Frontend (React + TypeScript)

- **Build tooling:** Vite.
- **Connections canvas:** the home screen (`/connections`) is a pannable/zoomable 2D board built on `@xyflow/react` (React Flow) — each saved connection is a draggable, resizable card (`ConnectionCard`). Position/size snap to a 40px grid that's aligned to the background dot pattern (`frontend/src/lib/canvasBounds.ts` — React Flow centers each dot within its cell rather than at the flow origin, so the snap grid is offset by half a cell to actually land on the dots, not between them). New cards are placed outward from the center of a bounded field (`CANVAS_BOUNDS`) rather than stacking in a corner.
- **SQL editor component:** CodeMirror 6 (schema-aware autocomplete, SQL syntax highlighting, good performance on large documents) — Monaco is a fallback option if CodeMirror's SQL tooling proves insufficient.
- **Data grids:** `ResultsGrid.tsx` renders arbitrary query results in the editor's resizable split and supports guarded inline cell updates when column provenance resolves to one primary-keyed table. `DataBrowser.tsx` is the dedicated table console: table selection, compound server-side filters, server-side pagination, add/edit/delete dialogs, explicit nulls/defaults, read-only state, and an “Open in query” bridge back to the SQL editor.
- **State/data fetching:** plain `fetch` wrappers (`frontend/src/lib/api.ts`) + Zustand stores per domain (`state/connections.ts`, `state/auth.ts`, `state/workbench.ts`, `state/jobs.ts`, `state/schema.ts`, ...) — connections, jobs, secrets, and saved queries are fetched from the backend on login and cached in the store, not persisted to `localStorage` (the backend is the source of truth for those; saved-query edits apply locally first and the list reloads from the server if a write is rejected). The Data view's remembered per-connection state is the deliberate exception (`state/dataView.ts`, device-local). A React Query-based data layer is still the plan if caching/invalidation gets more complex than the current fetch-on-load-and-optimistically-update pattern handles well.
- **Styling/component system:** Tailwind CSS + headless primitives (Radix UI) as the base, with a small custom design-token layer on top (see [DESIGN.md](DESIGN.md)) — not a heavy prebuilt component library, to keep the UI distinctive rather than looking like a generic admin template.
- **App-wide nav:** a collapsible left rail (`AppNavRail`, `@radix-ui/react-collapsible`) wraps every authenticated page — Connections, Workbench, Scheduled jobs, Settings — showing icon-only by default and expanding to icons+labels; expanded/collapsed state persists (`state/settings.ts`). Replaces the old per-page header icon buttons for cross-page navigation.
- **ERD layout (`SchemaDiagram.tsx`):** `dagre` decides each table's rank (dependency depth) and, within a rank, the crossing-minimized order — genuinely hard to reproduce by hand — but its raw pixel output is only a starting point, not the final layout, for two reasons found the hard way against a real "hub" schema (most tables referencing one directly, e.g. everything pointing at `users`): (1) dagre has no notion of a maximum column height, so a big rank becomes one absurdly long vertical file — tables are regrouped by rank after `dagre.layout()` runs (safe to do exactly, since every node shares the same width, so dagre gives same-rank nodes an identical x in LR mode) and any rank over 6 tables wraps into extra side-by-side sub-columns, still in dagre's own within-rank order; (2) fixed Left/Right connection handles funnel every edge into a hub table through the exact same point on its border — replaced with React Flow's documented "floating edges" pattern (`getNodeIntersection`/`getEdgePosition`/`FloatingEdge`), which computes each edge's actual attachment point per-render as the intersection of the straight line between the two tables' centers with each table's own rectangle, so connections spread around a hub's border instead of tangling into one line.

## 4. dbeans' own operator data

dbeans needs to persist things about itself, separate from the databases/streams it manages. **Current state:** `users`, `sessions`, `analytics_events`, `connections`, `jobs`, `job_runs`, `secrets`, `saved_queries`, and `saved_views` are implemented and live in the operator Postgres DB (`backend/internal/db`, migrated with plain `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` — no migration framework needed at this scale). The `connections` table holds each saved connection's engine-specific `fields` (JSONB), its canvas `layout` (JSONB — x/y/width/height), and a cached reachability `status` + `last_checked_at` (see §5 below); `jobs` holds a `job_type`, type-specific JSONB `config`, cron expression, `depends_on` (JSONB array of job ids), retry policy, and canvas layout. Query jobs retain their connection, SQL, and check mode in dedicated columns for backward compatibility; HTTP request jobs store URL, method, headers, and body in `config` and do not require a connection — plus two optional fields: `failOnNonEmptyArrayField` (also fail an otherwise-2xx run when a named top-level array field in the JSON response body is non-empty, for an endpoint that reports partial failures inside a successful-looking response) and `timeoutSeconds` (override the shared 20s request timeout for a job whose endpoint is legitimately slow, e.g. fronted by a cold-starting free-tier host — clamped to 5–280s). `job_runs` records every type's execution status/attempts/error/duration. Existing rows migrate automatically to `job_type = 'query'`. `secrets` is a per-user vault of named values referenced from query SQL or HTTP config as `{{name}}` — resolved by the same `renderJobTemplate` that handles `{{date}}`, checked *after* the reserved date/datetime names so a secret can't shadow them. Deliberately write-only: `secrets.value_enc` is AES-256-GCM-encrypted with the same `CONNECTION_ENCRYPTION_KEY` connections already use (no separate key to manage), and the API never decrypts it back into a response — only a name and `createdAt` ever round-trip to the frontend; editing means renaming and/or overwriting, never viewing the old value. The job editor's "Test query" button also resolves real secret values via an opt-in `renderTemplate` flag on `POST /api/connections/{id}/query`, so testing a job that references a secret doesn't just run the literal `{{name}}` text — ordinary workbench queries never set that flag, so `{{` stays literal there. First real usage: the Chesslab repertoire-refresh HTTP job's `X-Cron-Secret` header, originally a hardcoded token in `jobs.config`, was migrated to a `CHESSLAB_CRON_SECRET` vault entry referenced as `{{CHESSLAB_CRON_SECRET}}`. `saved_queries` (per user; PK `(user_id, id)`, client-chosen ids) holds the named queries the workbench's tab strip saves, listed in the sidebar and command palette — global to the user, not tied to one connection. `saved_views` holds named Data-browser presets (filters, sort, page size, column order/hidden) for one table of one connection: `config` is JSONB the server validates only as "a JSON object under 32 KB" (the frontend owns its shape), names are unique per user + connection + table, and rows cascade away with their connection or user. Both are served by `saved_queries.go` / `saved_views.go` (`GET/POST /api/saved-queries`, `PATCH/DELETE /api/saved-queries/{id}`, `GET/POST /api/connections/{id}/views`, `PATCH/DELETE …/views/{viewId}`), always scoped by `user_id` (a view additionally checks the connection is the caller's). Saved queries used to live only in the browser (Zustand `persist`, key `dbeans.snippets.v2`); on the first load after this shipped, `loadSnippets` moves whatever a browser still holds through the idempotent `POST /api/saved-queries/import` (`ON CONFLICT (user_id, id) DO NOTHING`, malformed entries skipped, original order kept via `clock_timestamp()`) and only then deletes the localStorage key, so a failed migration simply retries next load. **Still device-local by design:** the Data view's remembered state (last table, per-table filter/sort/page size/columns/widths, recent and pinned tables) lives in `localStorage` under `dbeans.dataview.v1` (`state/dataView.ts`) — it's the graphs date range's pattern, cheap to write on every change, and sanitized against the table's real columns on restore (`lib/dataView.ts`) so a stale entry can never send the server a filter it would reject. **Not yet implemented:** query history is still read back from `analytics_events` rather than a dedicated table (see the audit-trail paragraph below).

Two tables deliberately live outside the operator DB, in a *target* connection's own database instead, since a job's SQL only ever talks to its one connection (no cross-database queries): `job_run_metadata`, written by a job whose connection points back at the operator DB itself (a meta job logging other jobs' run history); and `dbeans_connection_stats`, written hourly per connection by a "Connection stats" job into that same connection's database (`database_size_bytes`, `active_connections`, `max_connections`, `table_count`, `total_row_estimate`, `engine_version`, `ssl_in_use`, `cache_hit_ratio`, `rollback_ratio`, `longest_query_seconds` — the last three added 2026-09-17, see below — keyed unique per `collected_hour` so re-running/backfilling it is a no-op rather than a duplicate row). The frontend's connection-graphs view (PRD.md) reads this table straight through the same `/api/connections/{id}/query` path the SQL editor uses — no dedicated backend endpoint for it.

**Graphs redesign (2026-09-17):** the connection-graphs tab dropped Authentication, TLS, and "last successful check" as standalone status cards — Authentication was really just "did the last stats job run succeed" mislabeled as a credential check, TLS was static config rather than a live signal, and "last successful check" duplicated Reachability's (renamed Status) own sub-label. In their place: `cache_hit_ratio`, `rollback_ratio`, and `longest_query_seconds`, all computable from standard Postgres system views with no extensions. A connection's "Connection stats" job needs its `INSERT` updated to populate them:
```sql
INSERT INTO dbeans_connection_stats (
  collected_at, collected_hour, database_size_bytes, active_connections, max_connections,
  table_count, total_row_estimate, engine_version, ssl_in_use,
  cache_hit_ratio, rollback_ratio, longest_query_seconds
)
SELECT
  now(), date_trunc('hour', now()),
  pg_database_size(current_database()),
  (SELECT count(*) FROM pg_stat_activity WHERE datname = current_database()),
  (SELECT setting::int FROM pg_settings WHERE name = 'max_connections'),
  (SELECT count(*) FROM pg_stat_user_tables),
  (SELECT COALESCE(sum(n_live_tup), 0) FROM pg_stat_user_tables),
  version(),
  (SELECT ssl FROM pg_stat_ssl WHERE pid = pg_backend_pid()),
  (SELECT round(100.0 * blks_hit / NULLIF(blks_hit + blks_read, 0), 1) FROM pg_stat_database WHERE datname = current_database()),
  (SELECT round(100.0 * xact_rollback / NULLIF(xact_commit + xact_rollback, 0), 2) FROM pg_stat_database WHERE datname = current_database()),
  (SELECT COALESCE(EXTRACT(epoch FROM max(now() - query_start)), 0) FROM pg_stat_activity WHERE state = 'active' AND datname = current_database() AND pid <> pg_backend_pid())
ON CONFLICT (collected_hour) DO UPDATE SET
  cache_hit_ratio = EXCLUDED.cache_hit_ratio,
  rollback_ratio = EXCLUDED.rollback_ratio,
  longest_query_seconds = EXCLUDED.longest_query_seconds;
```
**Bug found the hard way (2026-09-17):** the first version of this shipped querying `pg_stat_database` and `pg_stat_activity` with no `datname` filter, which aggregates across *every* database on the Postgres cluster/instance, not just this connection's own one. Invisible on a dedicated Postgres instance, but Chesslab Prod and Dbeans Prod share one Neon project (two databases, one instance) — both connections' cache hit ratio and rollback rate came out identical (and longest-running query could surface a slow query from the *other* connection's database), since every row read the whole cluster's counters. Fixed by adding `WHERE datname = current_database()` (and to the `pg_stat_activity` filter) so each connection only ever sees its own database. Anyone who copied the original version into their own job SQL should re-copy it with the `datname` filter.

Existing rows collected before a job adopts this are simply missing these three columns' values — the frontend renders "—" for nulls rather than failing, but the `SELECT` in `ConnectionGraphs.tsx` does require the columns to exist on the table, so a connection whose stats job hasn't been updated yet needs at least an `ALTER TABLE dbeans_connection_stats ADD COLUMN IF NOT EXISTS cache_hit_ratio numeric, ADD COLUMN IF NOT EXISTS rollback_ratio numeric, ADD COLUMN IF NOT EXISTS longest_query_seconds numeric;` run once before the graphs tab will load again. `job_run_metadata` is not created by `db.go`'s migration (it's user data from the meta job's own SQL, not a framework table) but does have real foreign keys back to `jobs`, `job_runs`, and `connections` — added by hand once, since a table that just happens to live in the same physical database as the operator schema should still participate in it relationally rather than sitting there as an orphan, especially now that the connection-diagram view (below) draws exactly the graph those foreign keys describe.

**Bug found the hard way (2026-09-16):** `job_run_metadata.connection_id` was created `NOT NULL`, back when every job necessarily had a connection. Once HTTP request jobs — which by design have `connection_id = NULL` — started producing `job_runs` rows (a couple of low-traffic ping jobs polling every 10 minutes), the meta job's own SQL (a single `INSERT ... SELECT ... FROM job_runs JOIN jobs`) hit that NOT NULL constraint on the first HTTP job's row and failed atomically — losing **every** job's metadata for that day, not just the HTTP job's, since the whole statement rolled back. This ran silently for two days (2026-09-14, 2026-09-15) before being noticed via the meta job's own `job_runs` entry showing `status = 'failed'`. Fixed by dropping the `NOT NULL` constraint on `connection_id` (the FK to `connections` already tolerates NULL with no schema change needed there); the two missing days were then backfilled by re-running the meta job's exact `INSERT ... SELECT`, substituting each missing date for `{{date}}` directly, and recording each as a `backfill`-triggered `job_runs` row (the original `failed` rows were left in place as accurate history rather than rewritten).

**Graphs follow-ups (2026-09-17):** the Status/Reachability card was dropped from the graphs view entirely, not just renamed — it's already shown on the connection's own canvas card, so repeating it here was pure redundancy. A date-range control (This week / This month / Custom) was added above the charts; it persists its last-used range per connection in `localStorage` (key `dbeans:graphs:range:<connectionId>`), the same device-local pattern the Data view's remembered state uses (§4 above) — best-effort, wrapped in try/catch, never blocking rendering if storage is blocked or unavailable. Caught before shipping further: formatting a local-midnight `Date` through `toISOString()` rolls the displayed calendar day back by one in any positive-UTC-offset timezone (UTC is still "yesterday" at local midnight) — fixed by building the date-input string from the `Date`'s local `getFullYear`/`getMonth`/`getDate` instead of round-tripping through UTC; the actual query bounds sent to Postgres still use `toISOString()` correctly, since those need to be real UTC instants, not display strings. Separately, failed runs in the outages list are now clickable, opening a dialog with the run's timing/attempts/trigger and its `job_runs.error` text — no new backend surface, since `GET /api/jobs/{id}/runs` already returns that column.

**Audit trail and Undo (2026-09-18):** every Data-view mutation now writes an `analytics_events` row (`row_insert`/`row_update`/`row_delete`/`bulk_row_delete`/`schema_change`, see §2) alongside the pre-existing `query_run` logging — closing a real gap where the Data editor could silently change or delete rows with no trail, unlike the SQL workbench. A short-lived toast offers "Undo" after each add/edit/delete, implemented entirely by re-invoking the same insert/update/delete endpoints with inverted arguments — there's no separate backend "undo" concept. Insert is undone by deleting the new row via the key its `RETURNING *` response handed back (needed for a database-generated primary key, which the request itself never knew); edit is undone by restoring the previous values the frontend already had on screen, merged with whatever new primary-key value was actually submitted so the right row is still found post-edit; delete is undone by re-inserting the same values, excluding any generated/identity column, since a plain `INSERT` can't supply an explicit value for one — so undoing the delete of a row whose primary key was itself database-generated restores its content but assigns it a new key, not the old one. Undo is not itself further undoable, and only ever acts on the most recent mutation (a new toast replaces whatever one was showing).

**Bug found the hard way (2026-09-18):** a query-optimization pass across every job's SQL and the backend's own queries (prompted by making sure the Data editor and jobs never scan more than they need to — see §2) turned up what looked like two indexes on `dbeans_connection_stats` covering the same column: its primary key, plus a separate `idx_dbeans_connection_stats_hour`. They looked redundant by analogy with this doc's own fixture examples elsewhere, where a table's PK *is* `collected_hour` — but Chesslab Prod's actual copy of this table has its PK on a separate `id` column instead, something not re-verified against this specific table before acting on the assumption. `idx_dbeans_connection_stats_hour` was in fact the *only* unique constraint on `collected_hour`, which the hourly "Connection stats" job's `INSERT ... ON CONFLICT (collected_hour) DO NOTHING` depends on to work at all — dropping it would have broken that job's very next tick with `there is no unique or exclusion constraint matching the ON CONFLICT specification`. Caught immediately by re-querying `pg_indexes` right after the drop, and the identical index was recreated before the next scheduled run. Lesson: check a specific table's actual constraints directly before calling an index redundant, rather than generalizing from a similarly-named table or example elsewhere. Once genuinely verified against the real data (row counts and existing index definitions, not assumptions), three narrower indexes were also added from the same review: `line_attempts_played_at_idx`, `book_study_activity_first_moved_at_idx`, and `today_training_queue_queue_date_idx` — every existing index on those three tables is composite and led by `username`, so "Daily user activity" and "Cleanup fact tables" (which filter by date only, across every user, with no `username` predicate) couldn't use any of them and fell back to a sequential scan. Harmless today (11–950 rows on those tables), but both are permanent daily jobs, so it'll start to matter as they grow.

## 5. Security model

- **Accounts:** real username/password accounts, not a single shared master password. Passwords are hashed with bcrypt (`golang.org/x/crypto/bcrypt`) before ever touching the database — `backend/internal/auth`. There is no self-serve signup; accounts are seeded server-side (`SEED_USERNAME`/`SEED_PASSWORD` env vars, applied once on startup, safe to leave set — it no-ops if the user already exists).
- **Sessions:** login returns an opaque random 32-byte token (hex-encoded), stored in the `sessions` table with an expiry (30 days) and sent back as a `Bearer` token on subsequent requests — no server-side JWT signing secret to manage, revocation is just a row delete (`/api/auth/logout`). Tokens are currently kept in the frontend's persisted Zustand state (`localStorage`); moving to an `HttpOnly` cookie is a follow-up hardening step once the frontend and backend are deployed behind the same origin.
- **Secrets:** `DATABASE_URL` (and any seed credentials) are read from environment variables only — `backend/.env` for local dev (gitignored, never committed) via `godotenv`, real platform env vars in production. `backend/.env.example` documents the shape without real values.
- **Brute-force protection:** the frontend enforces a client-side attempt counter and lockout window on failed logins; the backend itself does not yet rate-limit `/api/auth/login` — that's an open item before this is exposed beyond a trusted network.
- **Transport security:** dbeans assumes TLS termination happens in front of it (reverse proxy such as Caddy/nginx/Cloudflare Tunnel, or the PaaS's own edge) for any real deployment; the Go server itself speaks plain HTTP.
- **CORS:** the backend only allows the configured `ALLOWED_ORIGINS` (the frontend's own origin) — see `main.go`.
- **Query and table-mutation safety:** query jobs and freeform workbench queries run the user's own literal, hand-authored SQL directly (`conn.Query`), as expected for a SQL client using the user's stored database credentials. Generated table-editor SQL never interpolates cell/filter values: values use bind parameters, identifiers are metadata-validated and safely quoted, updates/deletes require a complete primary key, bulk deletes run in one transaction, views reject mutations, and read-only connections are enforced again on the backend. Visual schema actions use `/api/connections/{id}/schema-change`: the exact DDL is previewed and confirmed client-side, while the backend permits only a single `CREATE TABLE`, `ALTER TABLE`, or `CREATE [UNIQUE] INDEX` statement (no comments or additional statements) and applies the same read-only gate. HTTP request jobs can reach arbitrary HTTP(S) URLs and may contain credentials in their headers; use this only in a trusted single-user deployment because the backend has not yet added SSRF restrictions. Every Data-view mutation is additionally logged to `analytics_events` (`row_insert`/`row_update`/`row_delete`/`bulk_row_delete`/`schema_change`, see §4) and readable back per-connection via `GET /api/connections/{id}/history` — closing the gap where the Data editor could change or delete rows with no trail, unlike the SQL workbench's own `query_run` logging.
- **Connection reachability is a TCP check, not a login check:** `POST /api/connections/{id}/ping` (`backend/internal/api/ping.go`) dials the connection's `host:port` with a short timeout and records `online`/`offline`/`unknown` (SQLite is a local file path, not a host, so it's always `unknown`). This confirms something is listening, **not** that the stored credentials are valid — a scheduled job actually running against the connection is the real proof of that (see the "Connection stats" job pattern in §4, and the connection-graphs view's "Authentication" card in PRD.md, which is derived from that job's own run history rather than the TCP ping). Ping results are cached server-side for 60s per connection (`last_checked_at`), so the frontend can safely ping on every page load without hammering the target.

## 6. Deployment

- **Backend:** deployed and verified live via Vercel's **Go Framework Preset** (`backend/vercel.json` sets `"framework": "go"`) — this runs `backend/main.go` directly as a real Go server (`http.ListenAndServe`, reading `PORT` from the environment Vercel provides), *not* the older per-file `/api/*.go` serverless-function model. No request wrapper or rewrites needed; the existing chi router just works. The route/DB-setup wiring lives in `backend/internal/server` so the exact same code path also runs as a plain local binary (`go run .`) or on any traditional always-on host (Railway/Fly.io/a VPS), unchanged. Reads `DATABASE_URL`, `ALLOWED_ORIGINS`, `CRON_SECRET`, `SEED_USERNAME`/`SEED_PASSWORD` from the environment (see `backend/.env.example`). No local disk state — everything durable lives in the operator Postgres DB. See [DEPLOYMENT.md](DEPLOYMENT.md) for exact setup steps.
- **Frontend:** a separate Vite static build (`VITE_API_URL` pointing at wherever the backend is deployed), deployed as its own Vercel project (or any static host) — verified live, pointed at the Vercel-deployed backend above. Needs its own `frontend/vercel.json` with a catch-all SPA rewrite (`/(.*) → /index.html`) — without it, Vercel serves the static output literally and a reload/direct link to any client-side route 404s. The original single-binary plan (`go:embed` of `frontend/dist` into the Go binary) still stands as an alternative packaging for a non-Vercel, single-host deployment — not wired up, since the two-project Vercel split covers the current target.
- **Operator database:** any reachable Postgres works (developed against Neon); the backend runs its own migration on startup, so pointing at a fresh database is enough.
- **Scheduled jobs on Vercel:** there's still no persistent in-process scheduler once deployed there — one shared, secret-token-gated endpoint (`GET /api/jobs/tick?secret=...`, checked against `CRON_SECRET`) is hit by an external scheduler ([cron-job.org](https://cron-job.org)) on a fixed interval; the backend stores each job's own cron schedule (parsed with `github.com/robfig/cron/v3`) in Postgres and decides what's due on every tick, running each due job through dependency checks, retries, and its check — see [PRD.md](PRD.md). This means exactly **one** external cron entry ever needs to be configured by hand, not one per job; the exact tick URL is surfaced in Settings. **Caveat:** a job's retry delay sleeps synchronously inside the tick request, so a due job with a long `retryDelaySeconds` (or several due jobs in one tick, each retrying) risks the request's execution-time ceiling, whatever that ends up being for your specific Vercel plan/config — keep retry delays short if the job actually relies on retrying, or use the traditional-host path instead, which has no such ceiling.
- **Dependency-driven jobs don't use their own cron to trigger — they're driven by a persistent queue (`job_queue`).** The tick's due-jobs query only ever matches jobs with an empty `depends_on` (root jobs); anything with a dependency is excluded from cron matching entirely; its `cron_expr` is stored but purely informational. Instead, whenever a job succeeds, every job that depends on it gets a `job_queue` row for that same `run_date`, and every tick drains the queue: an entry runs the moment *all* of that job's dependencies have a recorded success for that exact `run_date` (stricter than the "most recent status, any date" check `executeJob` uses for a plain manual run), cascading through as many dependency levels as are ready and persisting across tick invocations if a chain doesn't fully resolve in one. This replaced an earlier design where a dependent job had its own cron entry offset a few minutes after its dependency's — that worked by spacing, not by actually waiting, since the tick's due-jobs query has no `ORDER BY` and two jobs due in the same tick could be evaluated in either order.
- **Cron scheduling is explicitly UTC-anchored** (`schedule.Next(time.Now().UTC())`, not bare `time.Now()`) — found the hard way running the backend locally on a non-UTC dev machine, where `next_run_at` silently got computed against the OS's local timezone instead. Vercel's containers happen to run in UTC by default, which is the only reason this wasn't visible in production, but relying on that implicitly was a latent bug.
- **The backend function's Vercel region matters a lot, because every query opens a brand-new connection** (`pgx.Connect`, no pooling — `backend/internal/api/query.go`). Left on Vercel's default (`iad1`, US East) while the operator DB is Neon's `ap-southeast-1` (Singapore), every single query paid for a full cross-continent TCP+TLS+Postgres-auth handshake — job durations sat around 2000-2200ms even for a trivial query against a table with a handful of rows. Setting `"regions": ["sin1"]` in `backend/vercel.json` (Vercel's closest region to Neon's) cut that to ~30ms, confirming it was essentially all connection-setup latency, not query time. If the operator DB or a heavily-queried target connection ever moves to a different region, this should move with it.
- **Both Vercel projects need Root Directory set (`backend`/`frontend`) for Git-triggered deploys to find the right code** — but doing so breaks `vercel deploy` run manually from inside that same subdirectory (it looks for a nonexistent nested `backend/backend`). The deploy workflow this project actually uses is `git push` → wait for the auto-deploy → `vercel alias set` against the new deployment, for both projects — see [DEPLOYMENT.md](DEPLOYMENT.md) for the full gotcha and why there's no configuration that makes both deploy paths work at once.

## 7. Key architectural decisions & rationale

| Decision | Rationale |
|---|---|
| Go backend | Good concurrency for query execution/streaming, no runtime dependency hell, matches the original plan. |
| `database/sql` + driver abstraction for SQL engines, separate clients for Redis/Kafka | Postgres/MySQL/SQLite share one API/query-execution path; Redis and Kafka aren't SQL, so they get their own thin driver interfaces instead of being forced into `database/sql`. |
| Real accounts (bcrypt + Postgres) instead of a single shared master password | User-requested pivot from the original single-password-vault plan; also unlocks per-user analytics and, later, per-user saved connections. |
| Operator data in Postgres (Neon) rather than local SQLite | Chosen when auth moved to real accounts — a hosted Postgres instance was already the natural home for `users`/`sessions`, and keeping analytics there too avoids a second storage system. |
| Bearer tokens instead of cookies (for now) | Simplest thing that works across the current separate-origin dev setup (Vite on one port, Go on another); revisit as an `HttpOnly` cookie once frontend and backend share an origin in production. |
| React + CodeMirror + Tailwind/Radix + cmdk | Modern, fast editor and command-palette experience; unstyled primitives keep the UI from looking like a generic admin template. |
| `@xyflow/react` for the connections canvas | Pan/zoom/drag/resize on a 2D board is a well-trodden problem; reusing a mature library (with a custom node component + our own grid-snap math layered on top) beat hand-rolling pointer-drag physics. |
| Connection reachability = TCP dial, not a real driver ping | Gives a genuinely real (not fake) status signal today without pulling in every engine's driver before query execution exists — see §5. Revisit once real per-engine connections are built; a real `Ping()` per driver would be strictly better. |
| One shared cron-triggered endpoint instead of one URL per job | Vercel has no persistent scheduler; an external trigger (cron-job.org) is required regardless, but a single shared "tick" endpoint means the *user* only ever configures one external cron entry, and all job scheduling logic/state lives in dbeans itself. |

## 8. Open questions

- Whether the Data view's remembered state (last table, per-table filters/sort/columns, pinned tables) should also sync across browsers. It is device-local today (`localStorage`, `dbeans.dataview.v1`) while named saved views are server-side; syncing it would need write-debouncing and conflict handling for little gain at one-user scale.
- Rate limiting `/api/auth/login` server-side (currently only client-side attempt counting).
- Moving the session token from `localStorage` to an `HttpOnly` cookie once frontend/backend share an origin.
- Whether query cancellation needs WebSockets or whether SSE is sufficient (leaning WebSocket for bidirectional cancel + status) — real query execution now exists (Postgres only), so this is no longer blocked on that, just not built yet.
- How much schema-introspection metadata to cache vs. re-fetch on each schema-tree expand (perf vs. staleness tradeoff — the frontend currently caches per connection for the session and only re-fetches on an explicit refresh click).
- Generalizing `backend/internal/api/query.go`'s Postgres-only introspection/execution into the multi-engine `Driver` abstraction described in §2, so MySQL/SQLite connections and jobs can actually run instead of erroring.
- Real per-engine job retry delays currently block the tick request itself (`time.Sleep` between attempts) — fine at personal-project scale, but worth revisiting (background workers / async retry) if job volume or retry counts grow.
